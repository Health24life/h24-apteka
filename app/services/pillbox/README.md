# Pillbox — таблетниця

План прийому препаратів користувача з акаунтом: які препарати, за якою схемою й курсом, у якому часовому поясі.
Моделі — `Pillbox::Plan` (план), `Pillbox::PlanItem` (препарат у плані) і `Pillbox::Intake` (факт прийому). Майбутні
прийоми не зберігаються: розклад обчислюється з правил препарату, а `Pillbox::Intake` тримає лише факти `taken`
(«Прийняв») і `missed` (пропущено). Звернень до провайдера тут немає.

## Ендпоінти

Гість на кожному ендпоінті отримує `401 unauthorized`, і для нього нічого не зберігається. Власник плану береться лише з
сесії: `user_id` у тілі ігнорується.

| Запит | Що робить |
|---|---|
| `POST /api/v1/pillbox/plans` | `201` і `{ plan }` з препаратами за `position`; невалідні дані — `422` з помилками всіх полів одразу |

## Створення плану (`Pillbox::Plans::Create`)

- **План**: `title` (обов'язкова, до 50 символів після обрізання пробілів), `timezone` (ідентифікатор IANA),
  `start_date` (за замовчуванням сьогодні за поясом плану, не раніше), `source_order_id` (бронь цього користувача, не
  кошик; бронь план не змінює).
- **Препарат** передається пласко, зі своєю повною схемою: `source` (`order` / `catalog` / `manual`), `goods_id`, `name`,
  `dosage`, `position`, `every_unit` (`day` / `week` / `month`), `every_n` (1–99), `weekdays` (лише для `week`, 0–6, 0 —
  неділя; порожньо — день тижня дати старту), `times` (1–6 значень `ГГ:ХХ` без повторів, зберігаються відсортованими),
  `reminder_mode` (`once` / `until_marked`), `course_mode` (`days` з `course_days` 1–365 / `until` з `course_end_date`
  від старту до старт + 365 / `open`).
- **Однакова схема для всіх** — справа клієнта: він розмножує схему по препаратах, а стан перемикача виводить з того, чи
  збігаються схеми. Сервер ознаки не має.
- **Джерело й товар** узгоджує клієнт. Сервер перевіряє лише, що `goods_id` є в каталозі; показує його каталог зараз чи
  ні, не має значення.
- Курс кожного препарату починається в дату старту плану (`course_start_date` = `anchor_date`). `schedule_version`
  нового препарату — 1, `missed_until` — момент створення.
- **Нормалізація** (`item.normalize!`, логіка — у `Pillbox::PlanItems::Normalize`) викликається явно сервісом, що
  записує препарати, а не на кожній валідації: `weekdays` порожні для не-`week` і відсортовані для `week`; для `days`
  обчислюється `course_end_date`, для `until` — `course_days`, для `open` обидва порожні. `times` сортує штатний
  `normalizes` моделі при присвоєнні. Новий сервіс, що записує препарати (правка плану), мусить викликати
  `item.normalize!` так само.
- **Власні перевірки препарату** зібрано в `Pillbox::PlanItemValidator`; у моделі — лише стандартні `validates`.

## Ліміти й помилки

- У плані 1–10 препаратів, у користувача до `Pillbox::Plan::MAX_OPEN_PLANS` (5) планів `active` + `paused`; завершені не
  рахуються. Ліміт рахується без блокування, тож одночасні створення можуть перевищити його: це м'яка межа.
- Помилки — стандартні помилки моделі Rails, `422` з `{ "<поле>": ["<текст>", …] }`. Препарат названо місцем у запиті
  (`items[1].times`, `index_errors` на `has_many :items`); ліміт препаратів — `items`, ліміт планів — `base`. Тексти
  стандартних перевірок поки англійською, власних (`too_many`, `too_many_plans`, `in_past`, …) — з `errors.messages`
  локалей. Окремих кодів помилок немає.
- План і препарати зберігаються одним `save`: якщо невалідне хоч одне поле, нічого не записується.

## Нагадування

Після збереження `Create` викликає `Pillbox::Reminders::TopUp` для нових препаратів: дозапланування нагадувань від
«зараз» до кінця вже запланованого вікна. Поки воно нічого не робить — нагадування з'являться разом із нічним
плануванням (H24N-3455) і відправкою (H24N-3456).

## Дані

Бізнес-правила живуть у моделях, а не в базі: жодних CHECK, унікальних чи часткових індексів, лише btree для пошуку.
Списки (`times`, `weekdays`) — `jsonb`, enum-и — рядки з Rails `enum`. Користувача ядра FK не зв'язує (інша БД), бронь і
товар — FK з `ON DELETE SET NULL`, таблиці таблетниці між собою — каскадом.
