# Pillbox — таблетниця

План прийому препаратів користувача з акаунтом: які препарати, за якою схемою й курсом, у якому часовому поясі.
Моделі — `Pillbox::Plan` (план), `Pillbox::PlanItem` (препарат у плані) і `Pillbox::Intake` (факт прийому). Майбутні
прийоми не зберігаються: розклад обчислюється з правил препарату, а `Pillbox::Intake` тримає лише факти `taken`
(«Прийняв») і `missed` (пропущено). Звернень до провайдера тут немає.

## Ендпоінти

Гість на кожному ендпоінті отримує `401 unauthorized`, і для нього нічого не зберігається. Власник плану береться лише з
сесії: `user_id` у тілі ігнорується.

Спільне для ендпоінтів — у concern `PillboxActions`: `no_store` і відмова гостю. Pundit (користувач — стандартний
`current_user`) і обробку помилок дає загальний concern `Exceptionable`, підключений в `ApiController`. План
шукається через `policy_scope` (`Pillbox::PlanPolicy::Scope`, лише плани користувача), тож чужий план —
`404 pillbox_plan_not_found`; препарат з `id`, якого немає серед незакритих препаратів плану, —
`404 pillbox_plan_item_not_found` (`Exceptionable` виводить код з моделі: `<модель>_not_found`).
`Pundit::NotAuthorizedError` — `403 forbidden`.

| Запит | Що робить |
|---|---|
| `POST /api/v1/pillbox/plans` | `201` і `{ plan }` з препаратами за `position`; невалідні дані — `422` з помилками всіх полів одразу |
| `PATCH /api/v1/pillbox/plans/:id` | `200` і `{ plan }` після всіх змін одним збереженням; `403 forbidden` для завершеного плану, `404` для чужого плану чи препарату, `422` з помилками полів |

## Створення плану (`Pillbox::Plans::Create`)

- **План**: `title` (обов'язкова, до 50 символів після обрізання пробілів), `timezone` (ідентифікатор IANA),
  `start_date` (за замовчуванням сьогодні за поясом плану, не раніше), `source_order_id` (бронь цього користувача, не
  кошик; бронь план не змінює).
- **Препарати** передаються списком `items_attributes` (`accepts_nested_attributes_for :items`, без `allow_destroy`:
  препарат прибирається закриттям, а не видаленням).
- **Препарат** передається пласко, зі своєю повною схемою: `source` (`order` / `catalog` / `manual`), `goods_id`,
  `name`, `dosage`, `position`, `every_unit` (`day` / `week` / `month`), `every_n` (1–99), `weekdays` (лише для
  `week`, 0–6, 0 — неділя; порожньо — день тижня дати старту), `times` (1–6 значень `ГГ:ХХ` без повторів,
  зберігаються відсортованими), `reminder_mode` (`once` / `until_marked`), `course_mode` (`days` з `course_days`
  1–365 / `until` з `course_end_date` від старту до старт + 365 / `open`).
- **Однакова схема для всіх** — справа клієнта: він розмножує схему по препаратах, а стан перемикача виводить з того, чи
  збігаються схеми. Сервер ознаки не має.
- **Джерело й товар** узгоджує клієнт. Сервер перевіряє лише, що `goods_id` є в каталозі; показує його каталог зараз чи
  ні, не має значення.
- Курс кожного препарату починається в дату старту плану (`course_start_date` = `anchor_date`). `schedule_version`
  нового препарату — 1, `missed_until` — момент створення.
- **Нормалізація** (`item.normalize!`, логіка — у `Pillbox::PlanItems::Normalize`) викликається явно сервісом, що
  записує препарати, а не на кожній валідації: `weekdays` порожні для не-`week` і відсортовані для `week`; для `days`
  обчислюється `course_end_date`, для `until` — `course_days`, для `open` обидва порожні. `times` сортує штатний
  `normalizes` моделі при присвоєнні. Новий сервіс, що записує препарати (правка плану), мусить викликати
  `item.normalize!` так само.
- **Власні перевірки препарату** зібрано в `Pillbox::PlanItemValidator`; у моделі — лише стандартні `validates`.

## Зміна плану (`Pillbox::Plans::Update`)

Інтерфейс зберігає всі правки однією кнопкою, тож усе приходить одним `PATCH`: `title` і `items_attributes`. Змінювати
можна план у статусі `active` або `paused` (`Pillbox::PlanPolicy#update?`); `timezone`, `start_date` і
`source_order_id` при правці не приймаються.

- **Препарат з `id`** змінюється. Зміна лише `name`, `dosage`, `position`, `source` чи `goods_id` версії схеми не
  змінює. Зміна будь-якого з `Pillbox::PlanItem::SCHEDULE_ATTRIBUTES` діє з поточного моменту: `missed_until = now`,
  `schedule_version + 1` (старі відкладені нагадування відсікаються), `normalize!`; `course_start_date` не змінюється.
  Якщо змінено `PERIOD_ATTRIBUTES` (`every_n`, `every_unit`, `weekdays`), відлік «кожні N» починається з сьогодні
  (`anchor_date = today`).
- **Препарат з `id` і `discard: true`** закривається: `discarded_at = now`, `missed_until = now`; факти прийомів
  лишаються. `discard` — віртуальний атрибут; `_destroy` не використовується, бо каскад видалив би історію.
- **Препарат без `id`** додається: `start!` (курс і відлік з сьогодні, власник плану, `missed_until = now`); без
  `position` іде в кінець списку. `discard` у нового препарату ігнорується.
- Закритий у тому самому збереженні препарат ще лежить в асоціації, тож кількість (1–10) рахується серед
  незакритих: закриття останнього — `422 items`. Після збереження `Update`
  скидає асоціацію (`items.reset`), і відповідь читає препарати знову через scope, без закритих.
- Змінений курс збереженого препарату не може закінчуватися раніше сьогодні (`in_past` на `course_days` або
  `course_end_date`); незмінений завершений курс правці інших полів не заважає.
- Ключі помилок — за порядком `items_attributes` (`index_errors: :nested_attributes_order`), а не за місцем у плані.
- **Пропущені прийоми.** Слоти до «зараз» за старими правилами поки не записуються як `missed`: зсув `missed_until`
  зроблено в одному методі (`close`), куди H24N-3458 додасть запис пропущених.

## Ліміти й помилки

- У плані 1–10 препаратів, у користувача до `Pillbox::Plan::MAX_OPEN_PLANS` (5) планів `active` + `paused`; завершені не
  рахуються. Ліміт рахується без блокування, тож одночасні створення можуть перевищити його: це м'яка межа.
- Помилки — стандартні помилки моделі Rails, `422` з `{ "<поле>": ["<текст>", …] }`. Препарат названо місцем у
  `items_attributes`, але ключ — за асоціацією (`items[1].times`, `index_errors` на `has_many :items`); ліміт
  препаратів — `items`, ліміт планів — `base`. Тексти стандартних перевірок поки англійською, власних (`too_many`,
  `too_many_plans`, `in_past`, …) — з `errors.messages` локалей. Окремих кодів помилок немає.
- План і препарати зберігаються одним `save`: якщо невалідне хоч одне поле, нічого не записується.

## Нагадування

Після збереження `Create` викликає `Pillbox::Reminders::TopUp` для нових препаратів, а `Update` — для нових і змінених
за схемою, лише для `active` плану (призупинений зберігає зміни без нагадувань): дозапланування нагадувань від
«зараз» до кінця вже запланованого вікна. Поки воно нічого не робить — нагадування з'являться разом із нічним
плануванням (H24N-3455) і відправкою (H24N-3456).

## Дані

Бізнес-правила живуть у моделях, а не в базі: жодних CHECK, унікальних чи часткових індексів, лише btree для пошуку.
Списки (`times`, `weekdays`) — `jsonb`, enum-и — рядки з Rails `enum`. Користувача ядра FK не зв'язує (інша БД), бронь і
товар — FK з `ON DELETE SET NULL`, таблиці таблетниці між собою — каскадом.
