# Catalog::Search — живий пошук товарів

Пошук товарів розділу «Аптека» для вебу й застосунку: `POST /api/v1/search`. **Локального пошуку немає** — кожен запит
іде наживо до провайдерів, а знайдене передається на фонове збереження в каталог. Тому збій провайдера — це збій пошуку
(`503`), а не порожня видача. Клієнт партнера описаний у [`pharmapoint`](../../pharmapoint/README.md), збереження
знайденого — у [`catalog/sync`](../sync/README.md) (дотягування на вимогу).

## Потік

```
Api::V1::SearchController#create
        │
        ▼
Catalog::Search::Queries::Build   (валідація queries, text, page, location → Query з округленою Location; Invalid → 422)
        │
        ▼
Catalog::Search::Run ──► Adapters.build ──► [Pharmapoint::Search, …]      (провайдери, яким дозволено пошук)
        │                                        │ один виклик, без повторів, у межах залишку дедлайну
        │                                        ▼
        │                    ProviderPage (hits + сирі записи груп)  або  Failure (:unavailable | :rate_limited)
        ├──► LocalGoods     (один запит: приховане — геть, збережене й показуване — ready: true з id і slug)
        ├──► Catalog::Sync::Pulls::EnqueueFound   (сирі записи → сховище → PullWorker; відповідь на це не чекає)
        └──► Metrics
        ▼
Result на кожен запит ──► ResponseBlueprint   або   503 search_unavailable / search_busy + Retry-After
```

| Файл | Навіщо |
|---|---|
| `../search.rb` | Простір імен, `Catalog::Search.config` і помилка `Invalid` з кодом поля |
| `queries/build.rb` | Розбір і валідація запитів із тіла звернення |
| `config.rb` | Налаштування пошуку (`dry-configurable`): провайдери, максимум запитів, дедлайн, точка й радіус |
| `adapters.rb` | Реєстр адаптерів за `provider.code`; провайдер без адаптера (зокрема власний) не шукається |
| `run.rb` | Обхід запитів × провайдерів під дедлайном, злиття, статус результату, передача знайденого |
| `local_goods.rb` | Видимість і `ready` рядків за каталогом |
| `metrics.rb` | Метрики пошуку й дотягувань (див. нижче) |
| `../../pharmapoint/search.rb` | Адаптер Pharmapoint: `goods-group/search` → нейтральні `Hit` і сирі записи груп |
| `app/value_objects/catalog/search/*` | `Query`, `Location`, `Hit`, `Failure`, `ProviderPage`, `Result` |
| `app/blueprinters/catalog/search/*` | Відповідь ендпоінта |

## Поведінка

- **Рядок** — SKU зі статичними даними картки: назва, форма, дозування, фасовка, торгова назва, виробник із кодом країни,
  рецептурність, група. Цін, залишків, ПДВ, кількості аптек і зображень немає. `ref` =
  `<код провайдера>:<id групи>:<id SKU>` — стабільний ключ, фронт його не розбирає.
- **`ready: false`** — SKU ще немає в каталозі або його знято з показу: без `id` і `slug`, відкрити чи покласти в кошик
  не можна. Після фонового збереження наступний пошук віддає його з `ready: true`. Прихований оператором SKU або група —
  рядка немає зовсім.
- **Пагінація** — у групах товарів: сторінка k у кожного провайдера; `per_page` і `total_groups` — суми по тих, хто
  відповів, `has_more` — якщо хоч у когось є наступна. Порядок — за `provider.id`, у кожного свій.
- **Статус результату**: `ok` — відповіли всі, `partial` — частина (перелік у `unavailable_providers`), `unavailable` —
  жоден, хоча інший запит того самого звернення вдався. Жоден запит не вдався → `503`: `search_busy` з `Retry-After`
  (найменший), якщо всі відмови — через ліміт, інакше `search_unavailable`.
- **Збої адаптера**: мережа, таймаут, 5xx — `unavailable`; частка пошуку, спільне вікно, `429` — `rate_limited`; 4xx,
  нечитне тіло, немає ключа, збій Redis — `unavailable` і `Rails.error.report`.
- **Персональні дані**: координати округлюються до 0.01° (~1 км) ще до звернення; телефон клієнта провайдеру не йде;
  `queries` відфільтровано в логах застосунку, текст лишається лише в журналі звернень (категорія `search`, 1 день).
- Кешування видачі немає: `Cache-Control: no-store`.

## Налаштування

Заглушки — у `mise.toml`, справжні значення — у `mise.local.toml`. Порожнє число — помилка на старті.

| Змінна | За замовчуванням | Що задає |
|---|---|---|
| `CATALOG_SEARCH_PROVIDERS` | `pharmapoint` | Коди провайдерів пошуку через кому. **Вимикач**: порожнє значення вимикає пошук (`503`), не чіпаючи `Provider.active`, тож синхронізація й дотягування працюють |
| `CATALOG_SEARCH_MAX_QUERIES` | `1` | Скільки запитів може бути в `queries` |
| `CATALOG_SEARCH_DEADLINE` | `4` | Секунд на все звернення, усі провайдери й запити разом |
| `APTEKA_SEARCH_DEFAULT_LATITUDE`, `APTEKA_SEARCH_DEFAULT_LONGITUDE` | Київ | Точка, коли фронт не передав координат (на пілоті — центр пілотного регіону) |
| `APTEKA_SEARCH_RADIUS` | `25000` | Радіус у метрах, коли фронт його не передав |
| `APTEKA_SEARCH_MAX_RADIUS` | `100000` | Більший радіус від фронта — `422` |
| `PHARMAPOINT_SEARCH_*` | див. [README клієнта](../../pharmapoint/README.md) | Таймаути, розмір сторінки й частка ліміту пошуку |

Передумови увімкнення в середовищі: заданий ключ партнера, імпортовані довідники й дерево категорій (інакше кожне
дотягування падає на `MissingReference`), точка за замовчуванням під пілотний регіон, ліміт запитів до API на Cloudflare.
Без ключа пошук у середовищі завжди відповідає `503`.

## Метрики

Метрики оголошені й рахуються через `yabeda` (`config/initializers/yabeda.rb`), але **збирача поки немає**: стек
моніторингу не узгоджений, тож ні адаптера (`yabeda-prometheus` чи іншого), ні ендпоінта збору в застосунку немає.
Збирач підключається гемом-адаптером і його налаштуванням, без змін у коді пошуку.

| Метрика | Теги | Що |
|---|---|---|
| `apteka_search_requests_total` | `status`: `ok`, `empty`, `partial`, `unavailable`, `busy` | Запити пошуку за результатом |
| `apteka_search_provider_answers_total` | `provider`, `status`: `ok`, `empty`, `unavailable`, `busy` | Відповіді провайдера |
| `apteka_search_provider_duration_seconds` | `provider` | Час відповіді провайдера (гістограма) |
| `apteka_search_rate_limit_share_left` | `provider` | Залишок частки пошуку в поточній хвилині |
| `apteka_search_pulls` | `provider`, `source`: `stash`, `provider` | Успішні дотягування груп за останню годину: зі сховища пошуку чи з повторним запитом |

Пошук рахує у веб-процесі, а дотягування йде в Sidekiq, тож `apteka_search_pulls` не рахується в іншому процесі, а
читається з журналу синхронізації в блоці `collect`. Цей блок запускає збирач, тому до його підключення
`apteka_search_pulls` порожня; решта метрик рахуються одразу.
