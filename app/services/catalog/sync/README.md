# Catalog::Sync — наповнення каталогу даними Pharmapoint

Фоновий імпорт статичних даних партнера в БД Health24: довідники, дерево категорій, групи товарів із SKU й розібраною
інструкцією, довідник аптек. **Ціна й залишок сюди не потрапляють** — вони завжди питаються наживо. HTTP-клієнт і журнал
звернень описані в [`pharmapoint`](../../pharmapoint/README.md).

## Потік

```
sidekiq-cron ──► StartWorker(kind) ──► Starter ──► RunTracker.start      (запис у журналі прогонів)
                                          │
                                          ▼
                              StepWorker(run_id, cursor) ──► StepRunner ──► Importers::<вид>
                                          ▲                         │          └─► Savers::* ─► BulkSave / Linker (запис + посилання на провайдера)
                                          └──── наступний крок ◄────┘
                                                    │ останній крок
                                                    ▼
                                      RunTracker.finish!  (+ Withdrawer для груп товарів)
```

Один вид даних — один прогін — один запис `SyncRun`; один крок — одна сторінка (або один пункт пошуку аптек, або весь
малий довідник). Воркери тонкі: усе, що вони роблять, — викликають сервіс.

| Вид (`kind`) | Крок | Курсор | Що зберігає |
|---|---|---|---|
| `dictionaries` | уся відповідь | — | форми, одиниці, цінові групи, температурні режими, обмеження, бренди |
| `categories` | все дерево | — | категорії з батьком і глибиною |
| `goods_groups` | сторінка `goods-group/search` | номер сторінки | група, виробник, торгова назва, клас АТХ, категорії, SKU, розділи інструкції |
| `drugstores` | пункт пошуку | індекс пункту | аптека, адреса з координатами, бренд |

Порядок наповнення: довідники → категорії → групи товарів. SKU посилається на довідники лише за ідентифікатором, тому
без довідників він іде в збій (`MissingReference`), а не зберігається з порожнім посиланням. Виробник, клас АТХ і категорії
групи створюються з даних самої групи, якщо їх ще немає.

## Налаштування

`Catalog::Sync::Config` (`dry-configurable`) — налаштування синхронізації, окремо від налаштувань партнера
(`Pharmapoint::Config`): пункти пошуку аптек (`PHARMAPOINT_DRUGSTORE_SEARCH_POINTS`), `stale_run_after`,
`stale_record_after` і група `pull` — строк сховища, пауза після збою й строк журналу дотягувань
(`CATALOG_SYNC_STASH_TTL`, `CATALOG_SYNC_PULL_COOLDOWN`, `SYNC_PULL_RUN_RETENTION_DAYS`). Значення зі змінних середовища
бере `config/initializers/settings.rb` і заморожує результат як `Catalog::Sync.config`.

### Пункти пошуку аптек (`PHARMAPOINT_DRUGSTORE_SEARCH_POINTS`)

Партнер не віддає весь довідник аптек одним запитом — лише аптеки навколо точки (`GET drugstore` з `latitude`,
`longitude`, `radius`). Тому змінна перелічує точки, навколо яких прогін `drugstores` збирає довідник.

Значення — **JSON-масив об'єктів**, рядок у змінній середовища:

```json
[
  { "latitude": 50.4501, "longitude": 30.5234, "radius": 50000 },
  { "latitude": 49.8397, "longitude": 24.0297, "radius": 30000 }
]
```

| Ключ | Тип | Що задає |
|---|---|---|
| `latitude` | число, градуси −90…90 | широта центру точки |
| `longitude` | число, градуси −180…180 | довгота центру точки |
| `radius` | ціле, метри | радіус пошуку навколо точки |

- Усі три ключі обов'язкові. Об'єкт без ключа чи зі значенням, що не є числом, — помилка на старті застосунку
  (`KeyError` чи `ArgumentError` з ініціалізатора), а не мовчазний пропуск точки.
- Невалідний JSON — теж помилка на старті (`JSON::ParserError`).
- Порожній масив (`[]`) чи порожня змінна — точок немає: прогін `drugstores` закривається `failed` з `ConfigurationError`.
- Незадана змінна — типове значення налаштування, тобто теж порожній список.
- Один крок прогону — одна точка, у порядку масиву. Аптека, яку повернули кілька точок, зберігається один раз, тож точки
  можуть перекриватися.
- У `mise.toml` — одна точка в центрі Києва з радіусом 50 км. Для пілоту точки підбираються під пілотний регіон.

Пошуку товарів ця змінна не стосується: місце пошуку задають інші налаштування (change пошуку).

## Цикл роботи

### 1. Старт прогону

1. `sidekiq-cron` за розкладом (`config/schedule.yml`) ставить `StartWorker(kind)`. Замок `until_executed` не дає
   поставити другий старт того самого виду, доки перший не виконався.
2. `Starter.call(kind)` викликає `RunTracker.start`:
   - прогони цього виду в статусі `running`, старші за `stale_run_after`, закриваються як `failed` (воркер, що впав, не
     блокує вид назавжди);
   - якщо прогін цього виду ще живий — нічого не відбувається;
   - інакше створюється `SyncRun` (`status: running`, `progress: { mode: 'full' }`).
3. У чергу йде перший крок: `StepWorker(run_id, first_cursor)`. Курсор першого кроку дає імпортер виду (сторінка `1`,
   пункт `0` або `nil` для виду з одного кроку).

### 2. Крок

`StepWorker` нічого не вирішує — лише викликає `StepRunner.call(run_id, cursor)`:

1. Якщо прогін уже не `running` (його закрили вручну або наступний старт визнав завислим), крок нічого не робить.
2. Для кроку створюються `RunTracker` прогону, `Pharmapoint::Client` (категорія журналу `refresh`, прив'язаний до
   прогону й номера спроби Sidekiq) і **новий `Linker`** — його кеш живе рівно один крок.
3. `Importers.for(kind).call(tracker, client, linker, cursor)` робить один запит до партнера, зберігає відповідь (див.
   нижче) і повертає курсор наступного кроку або `nil`.

Кожен запит клієнта:

- спершу проходить `RateLimiter` (Redis, спільний для всіх процесів): якщо хвилинний бюджет вичерпано або партнер
  попросив зачекати — `RateLimited`, і `StepWorker` ставить **той самий** крок у чергу через `retry_after`; це не
  рахується як спроба;
- пишеться в журнал звернень (`Provider::RequestLog`) з прогоном і номером спроби;
- `429` блокує всіх на `retry-after`; мережа й `5xx` → `TransientError` → повтор Sidekiq (до 5 разів, пауза `count⁴ + 15` с);
- `4xx` → `PermanentError`, невалідне тіло → `InvalidResponse` — крок **втрачено**: збій із `entity_type = 'page'`,
  позначка `partial`, прогін іде до наступного курсору (`Importer.skip`);
- немає ключа чи пунктів пошуку → `ConfigurationError` — прогін закривається `failed`.

### 3. Що робить імпортер кожного виду

- **`dictionaries`** — один запит, `Savers::Dictionary`: кожен із шести довідників одним пакетом (`BulkSave`).
- **`categories`** — одне дерево, `Savers::CategoryTree`: вузли поштучно, від кореня вниз, кожен під `guard`; гілка, батько
  якої не зберігся, чекає наступного прогону.
- **`goods_groups`** — одна сторінка `goods-group/search`, `Savers::GoodsGroup`:
  1. для кожної групи під `guard` — поштучно те, що їй потрібне до запису: виробник, торгова назва, клас АТХ із предками
     (від кореня); з цього складається `BulkSave::Entry` групи;
  2. групи сторінки — одним пакетом (`BulkSave`);
  3. для кожної збереженої групи під `guard` — категорії з її шляху (бракуючі створюються) і зв'язки з ними: зайві
     видаляються, позначка головної знімається й ставиться першій у списку партнера (`upsert_all`);
  4. `Savers::Goods`: для кожного SKU збережених груп під `guard` — атрибути й посилання на довідники
     (`Linker#fetch`, бракує довідника — `MissingReference`, SKU у журнал); SKU сторінки — одним пакетом; для кожного
     збереженого SKU під `guard` — `InstructionStore` (розбір лише коли змінився текст);
  5. у `progress` пишеться `last_page`; наступний курсор — наступна сторінка, після останньої — `nil`.
- **`drugstores`** — один пункт пошуку, `Savers::Drugstore`: кожна аптека поштучно під `guard` (з адресою й брендом);
  аптека зі списку без повних даних ставиться в чергу дотягування.

Лічильник `processed_count` росте на кожен збережений запис (атомарно, `update_counters`); `failed_count` — на кожен
запис у `SyncRun::Failure`.

### 4. Як пакет потрапляє в БД (`BulkSave`)

1. `Linker#preload` — записи пакета з їхніми посиланнями й перекладами одним запитом.
2. `Linker#build` — знайденому чи новому запису присвоюються атрибути, його посилання на провайдера отримує час кроку
   (`synced_at`); нічого не зберігається.
3. Записи діляться на змінені й незмінені (`changed_for_autosave?`: власні колонки або переклади).
4. Новим записам зі слагом слаг обирається заздалегідь, з урахуванням уже виданих у пакеті (імпорт не перевіряє
   унікальність).
5. Змінені записи валідуються, як при `save!`; той, що не пройшов, — у журнал. Порожні переклади, які створює читання
   з fallback-локаллю, прибираються (як це робить `before_save` Mobility).
6. Валідні — одним `INSERT … ON CONFLICT (id) DO UPDATE` у savepoint, з `recursive`: переклади й посилання пишуться
   разом із записом. Наявному запису оновлюються лише колонки, що змінились у пакеті, — `hidden`, зв'язок з ядром,
   картинку бренда пишуть інші, і синк їх не затирає.
7. Незміненим записам лише посувається посилання (`synced_at`, `updated_at`) одним `update_all`.
8. Імпорт позначає всі `has_many`/`has_one` збережених записів завантаженими (порожніми) — вони скидаються, щоб далі
   читатися з БД.
9. Будь-яка помилка пакета як цілого (відмова БД, значення, яке колонка не вміщує) → `Rails.error.report`, пакет
   відкочено, кеш моделі в `Linker` забуто, ті самі записи зберігаються **поштучно** через `Linker#sync` під `guard` —
   там кожен збій уже власний.

`Linker#sync` (поштучний шлях) бере запис із кешу кроку, а якщо крок бачив його відсутнім — перепитує БД перед
створенням: запис, який тим часом прив'язав воркер дотягування, оновлюється, а не дублюється.

### 5. Наступний крок

`StepRunner` пише курсор у `progress.cursor` і ставить `StepWorker(run_id, next_cursor)`. Кроки одного прогону йдуть
послідовно: наступний з'являється лише тоді, коли попередній закінчився. Замок `until_and_while_executing` тримає крок у
черзі один раз, але дозволяє кроку поставити себе ж повторно (очікування ліміту).

Якщо Sidekiq вичерпав повтори кроку, `sidekiq_retries_exhausted` викликає `StepRunner.give_up`: крок записується як
втрачена сторінка, прогін іде далі.

### 6. Завершення

Коли імпортер повернув `nil`:

1. Вид з одного кроку, крок якого втрачено й нічого не збережено, → `failed`.
2. Інакше `RunTracker#finish!`: `succeeded`, якщо збоїв немає й прогін не `partial`, інакше `completed_with_failures`;
   ставиться `finished_at`.
3. Для `goods_groups`, якщо прогін **не** `partial`, — `Withdrawer` (див. «Зняття з показу»).

Статуси прогону: `running` → `succeeded` | `completed_with_failures` | `failed`.

## Ізоляція збоїв

- Збій окремого запису пишеться в `SyncRun::Failure` (із вхідними даними без секретів), попередня версія запису
  лишається, прогін триває. Транзакції навколо сторінки немає.
- Довідники, групи товарів і SKU пишуться пакетом (`BulkSave`, див. «Цикл роботи», п. 4): невалідний запис іде в
  журнал, решта пакета зберігається; відмова пакета як цілого переводить його на поштучний запис.
- Поштучно, під `RunTracker#guard`, лишаються дерева (`closure_tree` веде таблицю ієрархії колбеками, які імпорт
  оминає): категорії й класи АТХ, а також виробники, торгові назви, зв'язки груп із категоріями, розділи інструкції й
  аптеки.
- Сторінка, яку партнер не віддав (4xx, невалідне тіло), записується як збій із `entity_type = 'page'`, прогін іде далі й
  закривається `completed_with_failures` та позначкою `partial`. Тимчасові помилки (мережа, 5xx, ліміт) повторює Sidekiq.
- Прогін із одного кроку, який не вдався, закривається `failed`. Прогін, який завис довше за `stale_run_after`, закриває
  наступний старт.
- Одночасно для одного виду працює не більше одного прогону (`RunTracker.start`).

## Ідемпотентність

`Linker` шукає запис за посиланням на провайдера (`Provider::Link`: провайдер, тип, зовнішній id), тому повторний імпорт
оновлює той самий запис, а не плодить дублі. Для пакета записи сторінки разом із посиланнями й перекладами знаходяться
одним запитом (`Linker#preload`); знайдене `Linker` пам'ятає до кінця кроку, тож посилання SKU на довідники не питаються
вдруге. Час посилання — коли запис востаннє бачили. Адреса картки (`slug`) створюється
один раз і далі не змінюється. Інструкція розбирається лише коли змінився її текст (`InstructionStore`).

## Зняття з показу

`Withdrawer` ставить `withdrawn` групам товарів і SKU, яких не побачив **повний прогін без пропущених сторінок**; нічого не
видаляється, запис, що знову з'явився, знову показується, а запис зі збоїв цього прогону не чіпається. Прапорець `hidden`
задає оператор — імпорт його не читає й не пише. Для аптек зняття вимкнене: довідник збирається за пунктами пошуку й не
охоплює всієї країни, тож відсутність аптеки у видачі нічого не доводить.

## Дотягування на вимогу

Усе дотягування живе в неймспейсі `Catalog::Sync::Pulls`: постановка одного запису (`Enqueue`) і сторінки пошуку
(`EnqueueFound`), сховище живої відповіді (`Stash`), пауза після збою (`Cooldown`), саме дотягування (`Runner`) і очистка
його журналу (`Retention`). Воркери — `Catalog::Sync::PullWorker` і `PullRunCleanupWorker`: Sidekiq зберігає ім'я класу
в поставлених завданнях, тож вони свої назви не змінюють.

```ruby
Catalog::Sync::Pulls::Enqueue.call(:goods_group, '122c4abff4ae26d0068e7b4cfce236a6', user_id: current_user&.id)
# => :enqueued | :queued_already | :present

Catalog::Sync::Pulls::EnqueueFound.call(provider:, found: records, user_id: current_user&.id)
# => { '122c…' => :enqueued | :queued_already | :present | :hidden | :paused }
```

`Enqueue` — для одного запису, якого немає в БД (аптека з неповними даними, первинне наповнення). Відповідь користувачу не
чекає. Запис, що вже є й не застарів (`stale_record_after`), не дотягується; неповну аптеку дотягують завжди. Без
`provider:` завдання йде без провайдера, і воркер бере типового (`Catalog::Sync::PROVIDER_CODE`).

`EnqueueFound` — для сторінки живого пошуку: `found` — сирі записи груп товарів із відповіді провайдера. Сторінка
перевіряється двома запитами (посилання груп і посилання SKU цього провайдера), а не двома на групу. Група ставиться в
чергу, якщо її немає, вона застаріла, знята з показу (`withdrawn`) або приносить SKU, якого в БД немає. Прихована
оператором група (`hidden`) і група на паузі після збою не ставляться. Збій постановки (Redis, вимкнений провайдер) іде в
`Rails.error.report` і на відповідь пошуку не впливає.

**Сховище живої відповіді (`Stash`).** Перед постановкою `EnqueueFound` кладе запис групи в `Rails.cache` під ключем
`catalog_sync_stash:<provider_id>:goods_group:<external_id>` на `CATALOG_SYNC_STASH_TTL` секунд (типово 600), а завдання
отримує цей ключ. Кладеться JSON без живих полів (`Pharmapoint::Readers::StashableGoodsGroup::LIVE_KEYS`) і лише повний запис:
з SKU, інструкцією в кожного SKU й категоріями групи — інакше збереження стерло б категорії чи інструкцію. Сховище
втрачальне: промах (TTL, витіснення, збій запису) означає звичайний `goods-group/get-by-id`.

**Виконання (`PullWorker` → `Runner`).** Аргументи — `(type, external_id, user_id, provider_id, stash_key)`; останні
два необов'язкові, тож завдання зі старої черги працюють через типового провайдера. Вимкнений чи відсутній провайдер — вихід
із `Rails.error.report` без запису в журналі. Спершу сховище: попадання зберігає групу без `Pharmapoint::Client` і не чіпає
ліміт. На промаху `RateLimiter#wait_time` (читання без витрати бюджету) перевіряється ще до відкриття запису журналу:
вичерпаний ліміт — `RateLimited`, Sidekiq повторює через `retry_after`, а збійного запису в журналі не лишається. Кожне
дотягування має власний короткий запис у журналі прогонів із `progress.mode = 'pull'` і `progress.source` (`stash` чи
`provider`); такі записи не враховує `SyncRun.last_successful`.

**Замок.** Один запис провайдера стоїть у черзі один раз: унікальний замок `until_executed` рахується за типом, зовнішнім id
і провайдером (користувач і ключ сховища не важливі). Той самий id у різних провайдерів — різні завдання. Замок тримається
через повтори (`RETRIES` = 8, `LOCK_TTL` покриває всі паузи між ними) і сам спливає, якщо воркер завис.

**Пауза після збою (`Cooldown`).** Коли запис не вдалося отримати чи зберегти (провайдер відмовив, запис не зберігся,
спроби вичерпано), у Redis ставиться `catalog_sync_pull_cooldown:<provider_id>:<type>:<external_id>` на
`CATALOG_SYNC_PULL_COOLDOWN` секунд (типово 900), і `EnqueueFound` цей запис не ставить. Інакше група з постійним
`MissingReference` журналювалася б на кожному пошуку.

**Очистка журналу дотягувань (`Retention`).** `PullRunCleanupWorker` за розкладом видаляє записи з
`progress.mode = 'pull'`, старші за `SYNC_PULL_RUN_RETENTION_DAYS` днів (типово 90), частинами; збої йдуть разом із
записом через зовнішній ключ. Періодичні прогони не чіпаються.

## Первинне наповнення

```bash
mise exec -- bundle exec rake 'one_time:catalog:pull_goods_groups[path/to/ids.txt]'
```

Файл — ідентифікатори груп товарів по одному в рядку. Таска ставить їх через ту саму чергу дотягування й друкує підсумок:
скільки поставлено, скільки вже було, скільки не вдалося. Порожній рядок чи рядок не того формату пропускається з
повідомленням.

## Запуск вручну й моніторинг

```ruby
Catalog::Sync::StartWorker.perform_async('drugstores')              # поставити прогін у чергу
Catalog::Sync::Starter.call('dictionaries')                         # або запустити зараз, у консолі
SyncRun.excluding_pulls.order(started_at: :desc).limit(5)           # останні прогони
SyncRun.last.failures.pluck(:entity_type, :external_id, :message)   # що не вдалося
Provider::RequestLog.where(sync_run_id: SyncRun.last.id)            # усі запити прогону
```

Прогони й збої видно також у панелі Sidekiq (вкладки Cron, Failures, Statuses). Кожен крок і дотягування пишуть запити в
журнал звернень із категорією `refresh`.

В адмінці (меню «Синхронізація» → «Прогони синхронізації») є список прогонів і дотягувань, картка прогону зі збоями й
посиланням на його звернення, а також кнопки ручного запуску. Кнопка є лише для виду, увімкненого в розкладі
(`Catalog::Sync::Cron.enabled?`); запуск іде через `Catalog::Sync::ManualStart` синхронно, тож адмінка одразу каже,
чи прогін поставлено в чергу, чи вид уже виконується. Ознаку «прихований» групам товарів, SKU й аптекам задає оператор
на їхніх картках у меню «Каталог» (`Catalog::Visibility::Changer`, причина — коментар на картці).

## Розклад

Задачі описано в `config/schedule.yml`; `sidekiq-cron` рендерить його через ERB і завантажує на старті Sidekiq. Cron
кожного виду береться з env-змінної `SYNC_CRON_*` (змінна й типове значення — у `Catalog::Sync::Cron`), cron чистки
журналу звернень — з `LOG_CLEANUP_CRON`, чистки журналу дотягувань — з `SYNC_PULL_RUN_CLEANUP_CRON`. Задачі з порожнім
cron у файлі немає, і `sidekiq-cron` прибирає її з Redis; вимкнений вид не можна запустити й вручну. Прогін груп товарів
вимкнений, доки з партнером не погоджено повний імпорт.

## Припущення, які ще не підтверджені

- Партнер, імовірно, не віддає весь каталог одним проходом, тому на старті основний механізм — дотягування й первинне
  наповнення за списком, а повний імпорт груп товарів лишається вимкненим.
- Повний довідник аптек не вичерпується одним запитом: пункти пошуку (`PHARMAPOINT_DRUGSTORE_SEARCH_POINTS`) — робоче
  рішення, а не відповідь партнера.
- Назви класів АТХ і країни виробників партнер віддає російською, українського джерела немає; вони зберігаються як
  отримані.
- Першою головною категорією групи вважається перша в списку партнера.
